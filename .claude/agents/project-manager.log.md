## [PM-2-1] 项目计划：Backlog 管理工具

- **阶段：** 2
- **状态：** completed
- **时间：** 2026-03-11T00:00:00

### 输入
用户需求：将现有简单任务管理器升级为 Python TUI Backlog 管理工具，支持增删改查、三态流转（Todo → In Progress → Done）、分类管理、搜索过滤、分类统计，数据本地存储。

现有代码分析：`src/task_manager.py` 已有基础的任务 CRUD、搜索、JSON 持久化，但缺少 TUI 界面、三态流转、分类功能。

### 输出

#### 里程碑清单

| # | 里程碑 | 完成条件 |
|---|--------|----------|
| M1 | 数据模型升级 | 任务模型支持三态状态（todo/in_progress/done）和分类（category）字段；现有单元测试通过 |
| M2 | 业务逻辑层完善 | 状态流转函数（todo→in_progress→done）、分类 CRUD、按分类/状态过滤、分类统计功能全部实现并有测试 |
| M3 | TUI 界面实现 | 基于 curses 或 rich/textual 的终端界面，支持键盘操作完成所有功能；可本地 `python main.py` 直接运行 |
| M4 | 集成测试与打磨 | 端到端流程测试通过，边界情况处理完善，用户体验打磨 |

#### 风险清单（按影响程度排序）

| 优先级 | 风险 | 影响 | 应对策略 |
|--------|------|------|----------|
| 高 | TUI 框架选型影响开发量 | 选错框架导致实现复杂度过高 | 建议使用 `textual` 或 `rich`；若需零依赖则用标准库 `curses` |
| 中 | 现有数据格式兼容性 | 升级后旧 tasks.json 无法加载 | 在 load_tasks 中加迁移逻辑，补充缺失字段默认值 |
| 中 | 全局变量架构不利于扩展 | 当前用全局列表存任务，TUI 中状态管理困难 | 重构为类封装（TaskManager class） |
| 低 | 终端兼容性 | 不同终端对 TUI 渲染效果不同 | 提供降级的纯文本模式或限定支持的终端 |

#### 任务依赖关系

```
M1（数据模型升级）
  ↓
M2（业务逻辑层完善）  ← 依赖 M1
  ↓
M3（TUI 界面实现）    ← 依赖 M2
  ↓
M4（集成测试与打磨）  ← 依赖 M3
```

M1 → M2 → M3 为严格串行依赖。M4 在 M3 完成后进行。

#### 模块建议划分

1. **model** — 数据模型升级（状态枚举、分类字段、TaskManager 类封装）
2. **logic** — 业务逻辑（状态流转、分类管理、搜索过滤、统计）
3. **tui** — 终端界面（视图渲染、键盘事件处理、交互流程）
4. **storage** — 持久化（JSON 读写、数据迁移）

其中 model 和 storage 可考虑合并为一个模块，logic 和 tui 各为独立模块。

#### 总体建议

1. **推荐零外部依赖方案**：使用标准库 `curses` 实现 TUI，避免安装依赖的摩擦。如果允许依赖，`textual` 提供更好的开发体验。
2. **优先重构数据层**：将全局变量封装为 `TaskManager` 类，这是后续所有功能的基础。
3. **模块串行开发**：由于强依赖关系，建议按 M1→M2→M3→M4 顺序串行推进。
4. **保持向后兼容**：加载旧格式 JSON 时自动补充 `category` 和新状态字段。

## [PM-3-1] 技术方案可行性评估

- **阶段：** 3
- **状态：** completed
- **时间：** 2026-03-11T22:35:00

### 输入
TechLeader 技术方案 [TL-2-1]，对比 PM 项目计划 [PM-2-1]

### 输出

#### 评估结论：方案可行，同意推进

TechLeader 的技术方案整体合理，可以按计划执行。以下是逐项评估：

#### 一、模块划分评估 — 合理

TL 划分为 model / repository / app / migration 四个模块，与 PM 建议的 model / logic / tui / storage 基本对应。TL 的划分更精确：
- 将 logic 和 storage 合并为 repository 层（SQLite CRUD + 业务逻辑），职责清晰
- migration 独立为单独模块，比 PM 方案中放在 storage 里更好，解耦更清晰
- 接口定义完整，各模块边界明确

**结论：** 优于 PM 原始建议，同意采用。

#### 二、技术选型评估 — 同意 Textual + SQLite

PM 原计划建议优先考虑零依赖的 curses 方案。经评估，TL 选择 Textual 更合理：
- Textual 提供 DataTable、Input、Select 等现成组件，开发效率显著高于 curses
- curses 需要手动处理布局、滚动、表单等，工作量大且容易出 bug
- 唯一外部依赖（textual>=0.50.0）可接受，pip install 即可
- SQLite 替代 JSON 存储：查询过滤和统计场景下性能和代码简洁度更优，Python 内置 sqlite3 无额外依赖

**结论：** 同意 Textual + SQLite 选型，撤回 curses 优先建议。

#### 三、开发顺序和并行策略评估 — 可行

TL 计划：model → repository → (app || migration)

对比 PM 原计划的严格串行（M1→M2→M3→M4），TL 方案在最后阶段实现了 app 与 migration 的并行，更高效。依赖关系正确：
- model 无依赖，先行开发 ✓
- repository 依赖 model ✓
- app 和 migration 都依赖 model + repository，互不依赖，可并行 ✓

**结论：** 并行策略合理，可行。

#### 四、风险补充

TL 已覆盖的风险与 PM 识别的基本一致。补充一点：
- **旧测试兼容性**：TL 计划保留旧 `task_manager.py`，这是正确的。但需确保新模块的测试不与旧测试冲突（如共享数据库文件路径）。建议测试中使用临时数据库（`:memory:` 或 tmpdir）。

#### 五、总体结论

| 维度 | 评估 |
|------|------|
| 模块划分 | ✓ 合理，接口清晰 |
| 技术选型 | ✓ Textual + SQLite 合适 |
| 开发顺序 | ✓ 并行策略可行 |
| 风险覆盖 | ✓ 基本完整，已补充测试隔离建议 |

**最终结论：方案可行，同意按 TL 技术方案推进开发。**
